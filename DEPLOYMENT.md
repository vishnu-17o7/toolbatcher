# Deployment Guide (Localhost + Vercel)

This guide explains how to run ToolBatcher in two environments:

1. Localhost (development or local testing)
2. Vercel (production-style deployment)

It also includes validation steps, required environment variables, and common failure cases.

## 1. Current Architecture

- Frontend: React + Vite in frontend/
- Backend: Express + MongoDB in backend/
- Install sessions: generated by backend APIs and consumed via bootstrap/runner endpoints

## 2. Prerequisites

- Node.js 18+
- npm 9+
- MongoDB instance (local or Atlas)
- Git
- Vercel account (for Vercel deployment)

Optional:

- Vercel CLI (npm i -g vercel)

## 3. Localhost Deployment

## 3.1 Install dependencies

Run from project root:

```bash
npm install
cd frontend && npm install
cd ../backend && npm install
```

## 3.2 Configure backend environment

Create backend/.env using backend/.env.example as reference.

Minimum required values:

```env
DATABASE_URL=mongodb://localhost:27017/toolbatcher
PORT=3002
FRONTEND_ORIGIN=http://localhost:5173
CORS_ALLOWED_ORIGINS=http://localhost:5173
TRUST_PROXY=false
```

Recommended security/runtime values:

```env
PUBLIC_BASE_URL=
JSON_BODY_LIMIT=200kb
INSTALL_MANIFEST_SECRET=replace-with-strong-secret
API_RATE_LIMIT_WINDOW_MS=900000
API_RATE_LIMIT_MAX=300
INSTALL_RATE_LIMIT_WINDOW_MS=600000
INSTALL_RATE_LIMIT_MAX=300
LOG_STARTUP_CONFIG=true
```

## 3.3 Start backend and frontend

Terminal 1 (backend):

```bash
cd backend
node index.js
```

Terminal 2 (frontend):

```bash
cd frontend
npm run dev
```

## 3.4 Validate localhost deployment

- Backend health: <http://localhost:3002/healthz>
- Backend API health alias: <http://localhost:3002/api/health>
- Frontend app: <http://localhost:5173>

Quick checks:

1. /healthz returns status=ok and expected runtime config fields.
2. Generate one-liner installer from UI and confirm URL points to localhost:3002.
3. Copy and open the bootstrap URL to confirm runner script is returned.

## 4. Vercel Deployment

Important: this repository currently contains several hardcoded frontend calls to <http://localhost:3002>.

Before Vercel deployment, replace those hardcoded values with a deploy-safe API base strategy (for example, a single config helper that reads VITE_API_BASE_URL). Current hardcoded locations include:

- frontend/src/components/AdminPage.jsx
- frontend/src/components/ToolSelector.jsx
- frontend/src/components/FeedbackForm.jsx
- frontend/src/components/admin/FeedbackList.jsx

Also review frontend/src/main.jsx, which currently sets axios.defaults.baseURL to a localhost value.

## 4.1 Recommended Vercel topology

Use two separate Vercel projects from the same repo:

1. Backend project (root directory: backend)
2. Frontend project (root directory: frontend)

This keeps backend environment and scaling policies separate from frontend static assets.

## 4.2 Backend on Vercel

The backend is Express-based, so for Vercel serverless deployment you need an adapter entrypoint (for example backend/api/index.js) and routing config (for example backend/vercel.json) that forwards requests into the Express app.

After adapter setup, configure these backend environment variables in Vercel:

Required:

- DATABASE_URL
- INSTALL_MANIFEST_SECRET

Strongly recommended:

```env
FRONTEND_ORIGIN=https://frontend.example.com
CORS_ALLOWED_ORIGINS=https://frontend.example.com
TRUST_PROXY=1
PUBLIC_BASE_URL=https://api.example.com
API_RATE_LIMIT_WINDOW_MS=900000
API_RATE_LIMIT_MAX=300
INSTALL_RATE_LIMIT_WINDOW_MS=600000
INSTALL_RATE_LIMIT_MAX=300
LOG_STARTUP_CONFIG=true
```

Backend validation after deploy:

1. GET <https://api.example.com/healthz> returns status=ok.
2. GET <https://api.example.com/api/health> returns status=ok.
3. CORS response allows only configured frontend origins.
4. One-liner generation returns URLs with your backend domain (or PUBLIC_BASE_URL if set).

## 4.3 Frontend on Vercel

Create a second Vercel project with root directory frontend.

Set frontend environment variables (if using env-based API routing):

```env
VITE_API_BASE_URL=https://api.example.com
```

Build settings:

- Build command: npm run build
- Output directory: dist

Frontend validation after deploy:

1. App loads without mixed-content or CORS errors.
2. API calls target your backend domain, not localhost.
3. Tool list, script generation, and install-session flow all work.

## 5. Cross-Origin and Security Checklist

Use this checklist for both staging and production:

1. CORS_ALLOWED_ORIGINS contains only trusted frontend domains.
2. TRUST_PROXY is enabled behind Vercel/proxies so protocol/IP are resolved correctly.
3. PUBLIC_BASE_URL is set if forwarded headers are altered by infrastructure.
4. INSTALL_MANIFEST_SECRET is strong and rotated when needed.
5. Rate limits are enabled (API and install sessions).
6. Health endpoints are reachable but do not expose secrets.
7. LOG_STARTUP_CONFIG is disabled if you do not want runtime metadata logs.

## 6. Smoke Test Script (After Deploy)

Run these checks manually:

1. Open /healthz and confirm JSON has:
   - status: ok
   - database: connected (or expected state)
   - corsAllowedOrigins list
   - rateLimits object
2. From frontend, generate a one-liner install session.
3. Confirm one-liner URL host matches backend domain.
4. Open bootstrap endpoint directly and confirm script is returned.

## 7. Troubleshooting

Backend returns 403 CORS:

- Add exact frontend origin to CORS_ALLOWED_ORIGINS.
- Verify protocol/domain match exactly (https vs http, www vs non-www).

Generated bootstrap URL points to wrong host:

- Set PUBLIC_BASE_URL explicitly.
- Ensure TRUST_PROXY is set correctly.

Install session API rate limit triggered too often:

- Increase INSTALL_RATE_LIMIT_MAX or window values.
- Verify traffic source and add upstream controls (WAF/CDN) if needed.

Frontend still calling localhost in production:

- Replace hardcoded localhost URLs in frontend source.
- Rebuild and redeploy frontend.
